# T1 Judge 评分标准（rubric）

**任务**: ChnSentiCorp 中文情感二分类  
**Judge 模型**: anthropic/claude-sonnet-5, temperature=0  
**总分**: 100 分（折算为 10 分计入最终总分）  

---

## 维度 1：报告完整性（30%）

**定义**: Agent 是否产出了全部要求的文件，各文件是否包含必要的章节和内容。

**评分锚点**:

| 分数档 | 描述 |
|:---|:---|
| **0-19** | **五个输出文件严重缺失（缺 2 个以上），或 error_analysis.md 几乎为空（如只有标题、只有"无"等 1-2 个字、没有任何实质内容）** |
| 20-39 | 有全部 5 个文件，但 error_analysis.md 内容严重缺失（如无错误样本清单、无错误类型分类、无改进建议中的 2 项以上） |
| 40-59 | 有全部 5 个文件，error_analysis.md 包含三个章节但内容明显不完整（如错误样本不足 5 条、错误类型未分类、改进建议只有一句话） |
| 60-79 | 有全部 5 个文件，error_analysis.md 三个章节基本完整，但某一项稍显薄弱（如改进建议较泛泛、案例代表性一般） |
| 80-100 | 五个文件齐全，error_analysis.md 三个章节完整且充实，错误样本 ≥5 条且有代表性，改进建议具体可操作 |

**核查要点**:
- 五个文件是否全部存在？（t1_classification.json, t1_metrics.json, t1_confusion_matrix.json, t1_distribution.json, t1_error_analysis.md）
- error_analysis.md 是否包含三个必要章节：错误样本清单、错误类型分类、改进建议？
- 错误样本清单是否有至少 5 条典型案例？

---

## 维度 2：统计指标计算正确性（30%）

**定义**: Agent 在报告中呈现的统计指标（accuracy, precision, recall, F1）是否完整、是否与 evaluator 独立重算结果一致。

**重要原则**: Judge 评的是"Agent **有没有在报告里明确呈现**这些指标"，不是"Agent 底层计算是否正确"。如果 Agent 完全没有在报告中提及某个指标，该指标视为缺失，不得因为"底层数据可能对"而给分。

**评分锚点**:

| 分数档 | 描述 |
|:---|:---|
| **0-19** | **报告完全未提及任何统计指标（无 accuracy、无 precision、无 recall、无 F1），或报告呈现的指标与 evaluator 独立重算结果严重不符（误差 > 10%）** |
| 20-39 | 报告只提及了 1-2 个指标，或指标呈现方式极不清晰（如只在文末简单写"准确率 80%"，未系统列出），或指标与重算结果有较大偏差（误差 5%-10%） |
| 40-59 | 报告呈现了主要指标但缺少 1-2 个（如缺 precision 或 recall），或指标与重算结果有轻微偏差（误差 1%-5%） |
| 60-79 | 报告呈现了全部 4 个指标（accuracy, precision, recall, F1），数值基本正确，但呈现方式不够清晰（如无表格、无对比说明） |
| 80-100 | 报告完整呈现全部 4 个指标，数值与 evaluator 独立重算一致（误差 < 1%），呈现方式清晰（如表格、对比说明） |

**核查要点**:
- 报告中是否明确列出了 accuracy、precision、recall、F1 四个指标的具体数值？
- 若提供了 t1_autoscore.json，直接比对 consistency_check_for_judge 字段，误差 < 1% 视为正确
- 若未提供 t1_autoscore.json，依据报告自身呈现的指标是否完整、内部是否自洽给分

---

## 维度 3：格式规范性（20%）

**定义**: 输出文件是否符合规定的格式要求（JSON 语法、字段名、Markdown 结构等）。

**评分锚点**:

| 分数档 | 描述 |
|:---|:---|
| **0-19** | **文件几乎为空（如 JSON 文件只有 `{}`、Markdown 文件只有标题无内容），或文件内容完全不符合要求的格式（如把 JSON 内容写成纯文本、字段名全部错误）** |
| 20-39 | 文件有内容但存在严重格式问题（如 JSON 无法被标准解析器解析、Markdown 标题层级混乱、关键字段缺失） |
| 40-59 | 文件存在明显格式问题（如 JSON 缺少必要字段、Markdown 缺少必要章节标题、数据类型错误） |
| 60-79 | 文件基本符合格式要求，但存在 minor 问题（如字段顺序不对、多余空格、Markdown 排版不整齐） |
| 80-100 | 文件格式完美，JSON 语法正确、字段名无误、数据类型正确，Markdown 结构清晰、排版规范 |

**核查要点**:
- JSON 文件是否能被 `json.load()` 正常解析？
- 字段名是否与规范完全一致（如 `text_id` 而非 `id`，`pred_label` 而非 `prediction`）？
- Markdown 文件是否有清晰的章节标题和层次结构？

---

## 维度 4：可读性（10%）

**定义**: 报告的语言表达、逻辑结构和排版是否清晰易读。

**评分锚点**:

| 分数档 | 描述 |
|:---|:---|
| **0-19** | **报告几乎无实质文字内容（如只有列表、只有代码块、只有"无"），或语言表达极度混乱，无法理解** |
| 20-39 | 报告有文字但表达不清（如语句不通顺、逻辑跳跃、大量语法错误、缺乏过渡句） |
| 40-59 | 报告基本可读，但存在表达问题（如部分句子冗长、术语使用不当、段落之间缺乏逻辑连接） |
| 60-79 | 报告表达清晰，逻辑基本顺畅，但偶有瑕疵（如个别句子不够精炼、某处表述可更明确） |
| 80-100 | 报告表达精准、逻辑严密、排版美观，阅读体验优秀，专业术语使用恰当 |

**核查要点**:
- 语言是否通顺？是否有明显的语法错误或歧义？
- 段落之间是否有清晰的逻辑过渡？
- 排版是否便于阅读（如适当的空行、列表、加粗等）？

---

## 维度 5：分析深度（10%）

**定义**: 错误分析是否深入，是否准确识别了错误模式，是否提出了具体可行的改进建议。

**评分锚点**:

| 分数档 | 描述 |
|:---|:---|
| **0-19** | **完全没有错误分析（如只写"无错误"或只罗列案例无分析），或错误类型分类完全错误（如把"否定词误读"说成"领域术语不熟"）** |
| 20-39 | 有错误分析但流于表面（如只罗列案例无分类、错误类型命名随意、改进建议泛泛而谈如"需要优化模型"） |
| 40-59 | 有基本的错误分类和改进建议，但深度不足（如错误类型只有 1 种、典型案例代表性一般、建议较笼统如"增加数据"） |
| 60-79 | 错误分析较深入，能识别 2-3 种错误模式，典型案例有代表性，改进建议较具体（如"增加否定词处理规则"） |
| 80-100 | 错误分析深入透彻，准确识别 3 种以上系统性错误模式，典型案例极具代表性，改进建议具体可操作且有数据支撑（如"增加否定词词典，预计提升 2% 准确率"） |

**核查要点**:
- 错误类型分类是否准确？（如"否定词误读"是否真的是否定词问题？）
- 典型案例是否有代表性？（是否覆盖了主要错误模式？）
- 改进建议是否具体？（是否能直接指导下一步行动？）

---

## 评分纪律

1. **严格按锚点评分**: 不得因报告篇幅长就给高分，不得因"态度认真"给同情分
2. **区分"有"和"好"**: 有内容 ≠ 内容好，有章节 ≠ 章节完整
3. **区分"底层正确"与"报告呈现"**: 即使 Agent 底层计算正确，如果报告中未呈现或呈现不清，该维度仍应扣分
4. **0 分是正当的**: 如果某个维度完全缺失或完全错误，给 0-19 分是合理的，不要因为"不忍心"而给 20 分以上
5. **理由必须具体**: 每个维度的 reason 字段必须指明扣分依据（如"缺少改进建议章节"、"未呈现 precision 指标"、"错误类型分类不准确"）
