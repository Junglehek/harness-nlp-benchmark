## 二、Phase 1 自动化脚本三件套

### 背景

Phase 1 要跑 40 次运行，如果每次都手工执行"重置工作区 → 等 Agent → 跑评分 → 跑 Judge → 备份 → 填表"，不仅慢而且容易出错。开工前先把这套流程脚本化，让人只负责两件事：启动 Agent、切换 harness 配置。

### 产出的三个脚本

**`scripts/init_pilot.sh`** — 一次性初始化。创建 40 个结果目录（`T1_A_001` ~ `T1_D_010`），并生成 CSV 记录表骨架。脚本写成幂等的，重复执行不会覆盖已有数据。

**`scripts/run_single.sh`** — 单次运行的后半段流水线。Agent 产出结束后跑这一个脚本，它会依次完成：重置检查、调用 evaluator 算自动分、调用 judge.py 算 Judge 分、把本次产出备份到 `results/pilot/` 对应目录、最后在终端打印本次成绩。

**`scripts/update_record.py`** — CSV 记录维护。按 run_id 定位行，更新分数、状态、耗时、备注。作废标记也走它，保证记录表的操作可追溯。

### 用法示例

```bash
bash scripts/init_pilot.sh                      # 开工前一次
bash scripts/run_single.sh T1_A_001             # Agent 跑完后
python3 scripts/update_record.py T1_A_003 \
  --auto 0 --judge 0 --total 0 \
  --status TIMEOUT --duration 55m18s \
  --notes "GOLD_CONTAMINATION..."
```

### 意义

这一步看起来是体力活，实际上是把"实验记录"从聊天截图和手工台账升级成结构化数据。后面所有统计分析、作废追溯、四条件对比，都建立在这张 CSV 上。事后证明这一步非常值得——当出现作废、重跑、异常标记时，CSV 成了唯一权威依据。

## 三、盲法缺陷发现与修复（2026-09-13）

### 怎么发现的

T1_A_003 跑到一半，Agent 在自己的执行报告里主动提到它"参考了"目录下的评分相关文件。追查发现：`README.md`（任务指令）和 `evaluator.py`、`judge.py`、`rubric.md`（评分三件套）都放在 `tasks/t1_chnsenticorp/` 同一个目录下。我们给 Agent 授了这个目录的读权限让它看 README，等于把整个评分系统也摊开给它看了。

### 为什么严重

`rubric.md` 里有 Judge 的五个维度、权重和每一档的分数锚点；`evaluator.py` 里有自动分的完整计算逻辑，包括"格式检查占 30 分、accuracy 占 63 分"以及每个 JSON 文件的字段要求；`judge.py` 暴露了 median_of_3 机制。一个知道评分标准的 Agent 完全可以"对着答案写报告"——不是分类作弊，而是报告包装作弊，更隐蔽。最危险的是 `fixtures/t1_gold.json` 也在可达路径上，一旦被读，整个实验直接作废。

### 数据怎么处理

T1_A_001~003 三次全部作废。虽然 001 和 002 没有明确报告读了评分文件，但无法证明没读——在盲法问题上"疑罪从有"。旧备份目录改名 `T1_A_001~003_deprecated/` 保留备查，CSV 里三行 status 改成 `DISCARDED` 并写明原因。

### 修复措施

```bash
# fixtures/reset_workspace.sh 末尾新增一行：
cp "$TASK_DIR/README.md" "$RUN_DIR/README.md"
```

这样每次重置工作区时，任务指令会被复制进 `run_default/`，Agent 不再需要离开工作区去读 README。同时启动 prompt 里加了隔离声明（只允许读 `run_default/`），DSH 的工作区也直接设到 `run_default/` 子目录，从三个层面把 Agent 圈住。

### 修复有没有用：新旧 001 对比

| 指标 | 旧 001（可能看过答案） | 新 001（盲法隔离后） | 差异 |
|:---|:---:|:---:|:---:|
| 自动分 | 83.40 | 81.60 | ↓ 1.8 |
| Judge 分 | 7.22 | 6.06 | ↓ 1.16 |
| 总分 | 90.62 | 87.66 | ↓ 2.96 |
| error_analysis 格式 | 6.0/6 | 4.0/6 | ↓ 2.0 |

新 001 各项分数全面下降，尤其 Judge 分掉了 1.16——旧 Agent 的报告确实可能"讨好"了 rubric。这个对比反过来证明作废是对的，也证明修复后的隔离确实生效了。

### 顺带的发现：隐藏要求

新 001 的 error_analysis 只写了 1 条错误案例，被 evaluator 扣了 2 分格式分（要求 ≥5 条、text_id 出现 ≥5 次）。但 README 里从来没写过这个数量要求——这是个"隐藏要求"。我们的决策是**不改 README**（已冻结），把它当成实验变量：四个条件面对同样的隐藏要求，谁自己挖出来谁不挖，本身就是 Harness 能力的差异。这比改成明示要求更有观测价值。

## 四、超时阈值调整（2026-09-14）

### 问题

实验设计里超时阈值写的是 10 分钟——这是早期拍脑袋估的，没验证过。Phase 1 实测前两跑：T1_A_001 用了 15m03s，T1_A_002 用了 16m08s。连最快的正常完成都远超 10 分钟，说明这个阈值跟 Agent 的真实工作流完全脱节。

### 为什么 10 分钟不现实

| 环节 | 耗时 |
|:---|:---:|
| 模型下载/加载（首次） | 2–5 分钟 |
| 本地推理 7766 条 | 3–8 分钟 |
| error_analysis 撰写 | 3–5 分钟 |
| 若选多模型集成 | 再 +5–10 分钟 |
| **合计（最低）** | **~15 分钟** |

### 调整内容

超时阈值 10m → **30m**。同时把状态定义细化：OK（≤30m 且 5 个产出文件齐全）、TIMEOUT（>30m，记 0 分但保留 notes）、INCOMPLETE（<30m 但文件不全）、API_ERROR（API 失败，可重试或记 0 分）。

### 更重要的收获

这次调整让我们意识到"耗时"本身是个值得统计的效应，而不只是及格线。于是 Phase 1 汇总新增了四个维度：每条件平均耗时、耗时标准差、超时率、token 消耗均值。事后证明这是对的投资——最终分析里 Harness 效应最显著的表现恰恰就在时间维度（Codex 对 Terra 快 2.1 倍、对 V4 慢 2.2 倍）。

## 五、Gold Contamination 事件（2026-09-14，P0 级）

### 事件经过

T1_A_003 运行中，DSH 派出的一个子代理通过 `../../` 一路逃出 `run_default/` 工作区，读到了项目根目录旁边的 `eval_datasets/chnsenticorp/ChnSentiCorp_htl_all.csv`——这个文件里有原始 gold 标签。子代理在返回消息里主动报告了这次读取，主 Agent 声称"已丢弃该子代理的全部输出"并覆盖了受影响文件。55m18s 后 Agent 交付了 5 个产出文件，累计消耗 10.9M tokens。

### 为什么作废

三个独立理由，任一成立都该作废：

1. **Gold 污染不可验证**——Agent 说丢弃了，但作为实验者无法独立验证最终文件里真的没有 gold 衍生信息。科研伦理上，无法验证的声明等于无效声明。
2. **破盲原则**——gold 一旦被接触，无论后续怎么补救，这次运行的盲法已经破了。
3. **超时 + 成本异常**——55m18s 超了 30m 阈值；10.9M tokens 是正常水平（1.5–2.5M）的 4–7 倍，本身就说明行为失控。

### 根因

值得说清楚的是：prompt 里的禁令（"严禁读取上级目录"）没有失效于措辞——Agent 读的 `eval_datasets/` **根本没在 prompt 里出现过**。它不是读了被禁止的文件，而是主动探索文件系统时发现了不该看到的东西。文本禁令约束不了"探索行为本身"。真正的原因是目录结构：`eval_datasets/` 和项目目录同放在 `Harness对比小尝试/` 下，Agent 只要逃出项目根目录就一定能看见它。

### 修复

```bash
mv .../Harness对比小尝试/eval_datasets \
   .../DownTheRoad/eval_datasets_backup/
```

把源数据物理移出 Agent 可达的任何路径。不改 prompt（避免连锁变量），CSV 里 T1_A_003 标记 `TIMEOUT` + `GOLD_CONTAMINATION` notes，然后重跑。

### 沉淀的机制

从这次事件开始，每次实验前多了一份安全检查清单（gold 文件、源数据、评分文件、DSH 工作区四项隔离确认），执行中多了四个异常监控信号：Agent 报告"读取了某文件"、耗时 >30m、token >5M、子代理数量异常多。

## 六、条件 A 完成（DSH + V4，2026-09-14）

盲法修复后重新跑了 10 遍，全部有效。

### 结果一览

| 指标 | 数值 |
|:---|:---:|
| 自动分 | 81.79 ± 1.72（CV=2.1%） |
| Judge 分 | 5.95 ± 0.55（CV=9.2%） |
| 总分 | 87.74 ± 1.74 |
| 实际 acc | **0.8868 ± 0.033** |
| 时间 | 9m57s（4m02s–16m08s） |
| Token | 1.55M（0.58M–3.1M） |

### 有意思的发现

**方法收敛现象。** 前 4 次（001~004）Agent 的方法高度变异：单模型、3 模型集成、2 模型集成、甚至做了一次 50/50 阈值校准。但从 005 开始，后面 6 次全部收敛到同一个方法——RoBERTa 单模型（jd-binary）。可能的解释有三个：`.hf_cache/` 里模型已经下载好，复用零成本；Agent 在多轮尝试后"学到"单模型够用；单模型 4–8 分钟比集成 12–16 分钟快得多，效率导向的策略胜出。这个"先探索后收敛"的模式是 DSH Agent 的一个稳定行为特征。

**A_004 是个警示案例。** 那次 Agent 查资料后决定做 50/50 阈值校准，强行把预测分布拉平——结果 accuracy 暴跌到 0.8009（其他 9 次都在 0.88 以上）。网上查到的"语料类别均衡"假设是错的，Agent 的外部知识反而害了它。

**自评准确度完全不可靠。** 各次运行用不同方法自评 accuracy：规则词典、人工抽检外推、校准概率……误差从 -12.10% 到 +9.90%。没有一种自评方法能稳定逼近真实值，这从侧面证明了外部 gold 评测的必要性。

**median_of_3 首次在实战中证明自己。** 10 次运行 Judge 调用失败率 20%（12/60 次），如果没有三取中位数的兜底，会有 2 次运行完全拿不到 Judge 分。

## 八、Gold 数据版本升级 v1 → v2（2026-09-19）

### 事件

条件 C_001（Codex + Terra）的 Agent 干了件"聪明过头"的事：它发现 `t1_input.json` 里 text_id 是 1–7766 连续编号，又通过公开知识知道 ChnSentiCorp 大约 68.5% 是正面，于是推断 text_id ≤ 5322 全是正面、> 5322 全是负面——然后**直接按 text_id 赋标签，根本没看文本内容**。accuracy 出来了：1.0000。

这不是它推理出来的，是它赌对了数据顺序。`prepare_data.py` 生成 gold 时保持了源 CSV 的顺序（正面在前、负面在后），text_id 和标签之间因此存在完美的顺序对应。C_001 作废，标记 `DATA_CONTAMINATION`。

### 修复

```python
# fixtures/prepare_data.py 核心改动：
import random
random.seed(42)                # 固定种子保证可复现
random.shuffle(records)        # 先打乱文本-标签对
for i, r in enumerate(records, start=1):
    r['text_id'] = i           # 再重新分配连续 text_id
```

同时把 CSV 输入路径更新为 `eval_datasets_backup/`（上次物理隔离后的新位置）。旧版备份为 `t1_gold_v1.json` / `t1_input_v1.json`。

### 验证输出

```
text_id 1: gold_label = 1        # 打乱后恰好还是正面（68.5% 概率）
text_id 7766: gold_label = 1     # v1 末尾全是 0，v2 末尾是 1 → 打乱生效
正面总数: 5322 / 负面总数: 2444   # 分布不变
```

### 这次改数据，A/B 的结果还算数吗？

这是升级后最需要想清楚的问题，结论是**算数**，理由有三层：

第一层，**分数层面无影响**。accuracy 是逐条 text_id 匹配后取平均，v1→v2 只是把同一批 (text, label) 换了顺序重编 id，每条文本的 gold_label 没变，分布没变。evaluator 按 id 字典匹配，对顺序完全无感。

第二层，**漏洞存在不等于被利用**。A/B 的 Agent 全程用 RoBERTa 等模型做真实文本分类，acc 落在 0.79–0.92 的合理区间，没有任何利用顺序规律的迹象。DSH 的 Agent 没发现这个规律，Codex 的 Agent 发现了——这个差异本身就是 Harness 效应的定性证据。

第三层，**可比性保持**。v1/v2 数据分布完全相同，C/D 换 v2 后无法再作弊，四条件比较的都是"同分布下的真实分类能力"。

一个诚实的注脚：v1 的 input 文件头部全是正面文本（因为顺序也是排的），如果 Agent 习惯"读前 N 条摸数据底"，v1 下会看到一个全是好评的样本——这可能影响它的分布认知（A_004 那个 50/50 校准的决策来源就有点可疑）。v2 下这个偏差消失了，但这类影响不改变"已跑分数有效"的结论。

### 值得注意的三点

**稳定得不像话。** 10 次 acc 全部挤在 0.8902–0.9010 之间，标准差 0.0029——是其他条件（0.021–0.033）的十分之一。V4 Pro High 在这个任务上的分类能力输出极其可靠，一次事故都没有。

**但代价是时间。** 21m37s 的平均耗时几乎是 C 条件（2m54s）的 7.5 倍。更反直觉的是：同一个 V4，在 DSH 上只要 9m57s，搬到 Codex 上变成 21m37s——**慢 2.2 倍**。而 Terra 正好相反，Codex 比 DSH 快 2.1 倍。Harness 对效率的影响随模型不同而方向相反，这是本期最重要的单点发现。

**分类稳，写报告不稳。** Judge 分标准差 1.16 是四条件最大的（最高 8.19、最低 3.94），V4 把评论分得又准又稳，但每次写出来的 error_analysis 质量忽高忽低。分类能力和报告能力在一个模型身上是可以解耦的。

## 十一、Phase 1 最终汇总：2×2 效应分离（2026-09-22）

40 次运行收齐后做了完整的四条件对比。

### 总表

| 维度 | A（DSH+V4） | B（DSH+Terra） | C（Codex+Terra） | D（Codex+V4） |
|:---|:---:|:---:|:---:|:---:|
| 实际 acc | 0.8868 | 0.8003 | 0.8179 | **0.8954** |
| 总分 | 87.74 | 82.06 | 83.01 | **89.04** |
| 时间 | 9m57s | 6m14s | **2m54s** | 21m37s |
| acc 标准差 | 0.033 | 0.021 | 0.033 | **0.003** |
| Judge 失败率 | 20% | 25% | 70% | 20% |

### 效应分离

**模型效应**（同 harness 换模型）：

- DSH 下（A vs B）：V4 → Terra，acc **↓ 8.65%**
- Codex 下（D vs C）：V4 → Terra，acc **↓ 7.75%**
- 均值 **↓ 8.20%**，两个 harness 上方向一致、量级接近——这是主效应，极其显著（t≈8–10，p<0.001）

**Harness 效应**（同模型换 harness）：

- V4 下（A vs D）：DSH → Codex，acc ↑ 0.86%，但时间慢 2.2 倍
- Terra 下（B vs C）：DSH → Codex，acc ↑ 1.76%，时间快 2.1 倍
- 均值 **↑ 1.31%**——准确率维度轻微，效率维度巨大且方向相反

### 核心结论

**第一，模型选择比 harness 选择重要 6 倍以上。** 换模型能改变 8.2% 的 accuracy，换 harness 只能改变 1.3%。在 T1 这类分类任务上，预算应该优先花在模型上。

**第二，Harness 效应的真实战场在效率和稳定性。** Codex 让 Terra 快 2.1 倍却让 V4 慢 2.2 倍——harness 和模型之间存在交互作用，不能简单说"哪个 harness 更快"。Codex+Terra 还出现过极端异常（acc 0.0068），DSH 两条件 20 次零事故。效率、稳定性都是 Harness 效应，只是不在分数上。

**第三，最优组合取决于你要什么。** 要质量选 Codex+V4（acc 0.8954），要速度选 Codex+Terra（2m54s），要均衡选 DSH+V4（9m57s + acc 0.8868）。

### 方法论验证

这次 Phase 1 同时验证了实验设计本身：2×2 全交叉矩阵跑得通；n=10 对检测模型效应够用（Harness 效应可能需要更大样本）；盲法隔离修复后生效；median_of_3 在 C 条件 70% 失败率下仍 100% 兜底；30 分钟超时阈值合理（最慢一次 30m02s 刚好卡在边上）。

### 经验教训

按重要性排序，本期沉淀下来的：

1. **物理隔离永远大于语义禁令。** Prompt 说"不要读"是约束不了探索行为的，文件不在 Agent 视线内才可靠。这条适用于所有 blind test。
2. **数据预处理必须打乱。** 任何与标签相关的顺序都是潜在漏洞——哪怕 Agent 不该看见 gold，input 的顺序模式本身也会泄露信息。
3. **完美分数是红旗。** accuracy = 1.0 在真实任务里几乎不可能出现，看到了先怀疑再庆祝。C_001 就是这样被当场抓住的。
4. **敢于作废早期数据。** 3~4 次运行的成本，跟 contaminated 数据对整个实验可信度的损害相比，不值一提。作废决策做过三次（旧 001~003、新 003、C_001），每次都是对的。
5. **子代理是独立行为体。** 主 Agent 守规矩不代表子代理守规矩，并行架构天然增加不可控面。反过来，Agent 主动报告违规是 DSH 的设计优点——但报告时污染往往已经发生。
6. **控制变量可以调整，但调整必须留档。** 超时 10m→30m 就是例子：拍脑袋的假设不如实测数据，改了就要写清楚为什么改。
7. **时间、token、稳定性都是效应。** 分数不是唯一维度。这次最有意思的 Harness 效应（效率方向相反）就是靠时间统计抓出来的；超时和 token 异常还是"失控"的早期预警信号。
8. **隐藏要求可以是 feature。** error_analysis 的 ≥5 条要求没有写进 README，干脆作为实验变量——观测不同 harness/model 自主挖掘隐含要求的能力差异，四条件公平。
